🔹 Introduction
Q1
Project Overview

Walk me through EduNexus. What problem does it solve, how did you architect it, and what were the biggest technical challenges you personally solved?

🔍 What the Interviewer Is Testing

Whether you actually built it, understand the big picture, can articulate decisions, and distinguish your contribution from boilerplate.

✅ Strong Answer

EduNexus is a review management platform for academic institutions — think of it as a structured feedback loop between students, faculty, and admins. The core problem was that institutions were managing review cycles over email, which caused delays, lost submissions, and no audit trail.


Architecturally, I went with a decoupled MERN setup — React SPA on the frontend talking to an Express REST API. MongoDB made sense because the review schema is semi-structured and evolves with each institution's workflow. I used Redux Toolkit for global state because I needed auth state, notification badge counts, and real-time messages to be accessible across deeply nested components.


The three things I personally owned that were most complex were: (1) the JWT + RBAC middleware pipeline — making sure each route enforces role and ownership checks without duplicating logic; (2) the Socket.IO room system — each user joins their own userId room so targeted notifications don't broadcast to everyone; and (3) the Docker + Nginx production setup on EC2, where I debugged an HTTP/2 protocol error that was silently breaking login responses in production.

💬 Follow-Up the Interviewer Will Ask

You mentioned the HTTP/2 issue in production. What exactly was happening and how did you find the root cause?

🎯 How to Respond

The frontend on Vercel was hitting the EC2 backend through Nginx. Login POST requests were returning ERR_HTTP2_PROTOCOL_ERROR. The JWT response body was being sent, but the browser was dropping it. I checked Nginx error logs — saw stream reset errors. Nginx was negotiating HTTP/2 with the Express backend, but the Express server wasn't an HTTP/2 server — it was plain HTTP. So Nginx was forwarding in HTTP/2, Express replied in HTTP/1.1, Nginx couldn't translate the response back cleanly. Fix was simple: disabled HTTP/2 in the Nginx listen directive — changed listen 443 ssl http2 to just listen 443 ssl. Verified in Chrome Network tab that responses started coming through immediately.

🔹 React & State Management
Q2
React ArchitectureRedux Toolkit

Why Redux Toolkit over React Context? In a review management app how much state actually needed to be global?

🔍 What the Interviewer Is Testing

Whether you blindly used Redux because everyone does, or made a conscious trade-off decision. They want to catch over-engineering.

✅ Strong Answer

Honestly, I considered Context first for auth. But the moment I added real-time notifications — where the bell icon, the notification list, and the chat badge all need the same live data — I realized Context would cause excessive re-renders across the tree every time a Socket.IO event came in.


What ended up in Redux was limited: auth slice (user, token, role), notification slice (unread count, notification list), and chat slice (active conversation, unread messages). Everything local — form state, loading spinners, modal open/close — stayed in useState. I used RTK Query for API calls on the heavier data-fetching pages like admin dashboards, so I got caching and auto-refetch for free without writing thunks manually.

💬 Follow-Up

When a Socket.IO event arrives, exactly how does it update Redux and re-render the notification bell?

🎯 How to Respond

In a top-level component (I put it in App.js inside a useEffect), I listen to the socket event — say socket.on('new_notification', (data) => { dispatch(addNotification(data)) }). The addNotification reducer in the notification slice pushes to the array and increments the unread count. The bell component is connected via useSelector so it re-renders only that component, not the whole tree. That's the key advantage over Context — Redux's selector subscription is surgical.

🔹 Authentication
Q3
JWT Auth

Walk me through your exact JWT implementation — token generation, storage on client, and how it's sent on every request. What happens when the token expires?

🔍 What the Interviewer Is Testing

Security awareness — localStorage vs cookies, token expiry handling, refresh token strategy, and whether you understand XSS vs CSRF trade-offs.

✅ Strong Answer

On login, the backend signs a JWT with jsonwebtoken — payload includes userId, role, and iat. I set a 1-day expiry for the access token. On the client, I store it in localStorage and set it in the Redux auth slice. Every API call goes through an Axios instance with a request interceptor that attaches Authorization: Bearer <token>.


For expiry handling — when the server returns a 401, the Axios response interceptor catches it, dispatches a logout action to clear Redux and localStorage, and redirects to login. I didn't implement refresh tokens in v1 — which is a known gap. If I were scaling this, I'd add an httpOnly cookie-based refresh token so the access token can be short-lived (15 min) and the refresh token is XSS-safe.

💬 Follow-Up

Why is storing JWT in localStorage a security risk? How would you fix it without breaking your current flow?

🎯 How to Respond

localStorage is accessible to any JavaScript on the page — so if there's an XSS vulnerability anywhere (a third-party script, unsanitized user input rendered as HTML), an attacker can steal the token. The fix is to store the JWT in an httpOnly; Secure; SameSite=Strict cookie, which JavaScript can't read. The backend sets it via Set-Cookie header. On the frontend I'd remove the Axios Authorization header interceptor — the browser sends the cookie automatically. The trade-off is CSRF vulnerability, which I'd mitigate with a CSRF token or by using SameSite=Strict which blocks cross-origin requests from sending the cookie.

Q4
RBAC

How did you implement role-based access control? Show me the flow from route definition to what happens if a student hits an admin-only endpoint.

🔍 What the Interviewer Is Testing

Whether RBAC is just frontend-guarded (which is insecure) or properly enforced on the API layer.

✅ Strong Answer

I have two middleware layers. First is verifyToken — it reads the Authorization header, calls jwt.verify(), and attaches req.user (userId + role) to the request. Second is authorizeRoles(...roles) — a factory function that returns middleware checking if req.user.role is in the allowed list.


In the router: router.delete('/user/:id', verifyToken, authorizeRoles('admin'), deleteUser). If a student hits that endpoint, verifyToken passes (token is valid), but authorizeRoles checks the role from the decoded token — not the database, not the frontend — and returns a 403 with a message like "Access denied: insufficient role". The key is the role is embedded in the signed JWT, so it can't be tampered with client-side.

⚠️ Gap to acknowledge: If an admin's role changes in the DB while their token is still valid, they'd retain elevated access until the token expires. The fix is to validate the role against the DB on sensitive actions, or use short-lived tokens.
💬 Follow-Up

What about ownership checks? Can Student A see Student B's reviews?

🎯 How to Respond

Role check alone isn't enough — that's authorization vs ownership. In the controller, after confirming the role, I also compare req.user.userId against the document's owner field. For example, a student can only fetch reviews where review.submittedBy === req.user.userId. For admin routes, ownership is bypassed. I push the ownership filter directly into the MongoDB query — Review.find({ submittedBy: req.user.userId }) — rather than fetching all and filtering in JS, which would be a data leak risk.

🔹 Database Design
Q5
MongoDB Schema

Describe your MongoDB schema for a Review. Why did you choose embedding vs referencing for related data like faculty and student info?

🔍 What the Interviewer Is Testing

Schema design decisions, understanding of embedding vs referencing trade-offs in document databases, and awareness of data growth implications.

✅ Strong Answer

My Review schema has submittedBy (ref to User), assignedFaculty (ref to User), content, status (enum: pending/approved/rejected), mode (online/offline), scheduledAt, and meetingLink. I used references rather than embedding for user data because user profiles change — if I embedded the student's name and it changed, I'd have stale data across hundreds of reviews. With references I do a .populate() when I need the full profile.


The one thing I did embed was a history array — each time a review's status changes, I push { status, changedBy, changedAt, comment } into an array on the review document. That made sense to embed because it's append-only, tightly coupled to the review lifecycle, and I always query it together with the review — never independently.

💬 Follow-Up

If a student submits 5,000 reviews, will that history array cause problems?

🎯 How to Respond

Good catch. MongoDB has a 16MB document size limit. Each history entry is maybe 200–300 bytes — so 5000 entries is around 1.5MB, which is fine. But if this were a high-throughput system, I'd separate history into its own ReviewAuditLog collection with a reviewId reference, paginate it separately, and only return the latest 5 entries with the review. That keeps the core review document lean and queries fast.

Q6
MongoDBIndexing

What indexes did you create in MongoDB? How do you know your queries are actually using them?

🔍 What the Interviewer Is Testing

Whether you just define schemas and hope for the best, or actually think about query patterns and verify performance with explain plans.

✅ Strong Answer

The two most frequent queries drove my indexing decisions. Students always fetch their own reviews — so I indexed { submittedBy: 1, status: 1 } as a compound index. Admin fetches reviews by faculty and date range — so { assignedFaculty: 1, scheduledAt: -1 }. For the notification system, I index { recipient: 1, read: 1 } so unread count queries are fast.


To verify they're being used, I ran .explain("executionStats") on critical queries in Compass and confirmed IXSCAN instead of COLLSCAN. I also looked at totalDocsExamined vs nReturned — if those numbers are far apart, the index isn't selective enough. The email field on the User model has a unique index implicitly because I set unique: true in the Mongoose schema.

💬 Follow-Up

What's the difference between a covered query and a regular indexed query?

🎯 How to Respond

A regular indexed query uses the index to find document IDs and then fetches the full documents from storage — two I/O operations. A covered query means all the fields you're projecting are inside the index itself, so MongoDB never needs to touch the actual documents — it serves the response entirely from the index. For example, if I query { submittedBy: userId } and project only { status: 1 }, and my index is { submittedBy: 1, status: 1 }, that's a covered query. It's significantly faster at scale because it reduces disk I/O.

🔹 API Design
Q7
REST API

If I call GET /api/reviews as a student vs as an admin, does it return the same data? How does your API handle that?

🔍 What the Interviewer Is Testing

API design maturity — shared controller logic with conditional behavior based on role, vs separate endpoints. Also tests understanding of data leakage risks.

✅ Strong Answer

I have one controller function but it branches on req.user.role. If the caller is a student, the query is Review.find({ submittedBy: req.user.userId }). If admin, it's Review.find({}) with optional filters from query params like ?status=pending&faculty=id. Faculty gets Review.find({ assignedFaculty: req.user.userId }).


Alternatively, I could have three separate endpoints — /api/student/reviews, /api/admin/reviews, /api/faculty/reviews — which is actually cleaner for large teams because each route is explicit and auditable. The shared controller approach is DRY but if the logic branches heavily, it becomes hard to maintain. I'd reconsider the separation at scale.

💬 Follow-Up

What HTTP status codes do you return for validation errors, auth failure, and server crash?

🎯 How to Respond

400 for validation errors — missing or malformed fields. 401 for unauthenticated — token missing or invalid. 403 for authenticated but not authorized — wrong role. 404 for resource not found. 409 for conflicts — like registering with a duplicate email. 500 for unhandled server errors, but I catch those in a global Express error handler so I never send a stack trace to the client — I log internally and return a generic message.

🔹 Real-Time System
Q8
Socket.IO

Explain exactly how your Socket.IO notification system works — from when a review is submitted to when the faculty sees a notification badge update in real-time.

🔍 What the Interviewer Is Testing

Deep Socket.IO knowledge — rooms, targeted emission, event patterns, and whether you understand the gap between HTTP REST and WebSocket.

✅ Strong Answer

When the server starts, I initialize Socket.IO on the same HTTP server Express uses. On the client, when a user logs in, they connect to the socket and emit a register event: socket.emit('register', userId). On the server side, the register handler calls socket.join(userId) — so each user is in their own room named after their userId.


When a student submits a review, the REST controller saves the review to MongoDB and then — in the same async function — emits: io.to(facultyId).emit('new_notification', { type: 'review_submitted', ... }). Only the faculty member in that room receives it. On the React side, the faculty's socket listener calls dispatch(addNotification(data)), the Redux slice increments the unread count, and the bell icon re-renders with the new count.

Key insight: The socket server needs access to io inside the Express controller. I solved this by attaching io to app.locals.io = io at server startup and accessing it via req.app.locals.io in controllers — keeps it clean without global variables.
💬 Follow-Up

What happens if the faculty member is offline when the notification is emitted? Is it lost?

🎯 How to Respond

Yes, in my current implementation the Socket.IO event is lost if they're offline — Socket.IO doesn't persist events. That's why I also persist every notification to MongoDB before emitting the socket event. When the faculty logs back in and loads the dashboard, they call GET /api/notifications?read=false which fetches unread notifications from the DB. The socket is only for the real-time "push" experience — the DB is the source of truth. This is the "dual write" pattern: database for durability, socket for immediacy.

Q9
Socket.IOConcurrency

What if 100 students submit reviews at the same time? Walk me through potential race conditions or bottlenecks in your system.

🔍 What the Interviewer Is Testing

Understanding of Node.js's single-threaded event loop, MongoDB's document-level locking, and awareness of system limits under load.

✅ Strong Answer

Node.js handles this well at the I/O level — 100 concurrent requests don't block each other because each await Review.save() releases the event loop thread while waiting for MongoDB. No race condition on the review creation itself because each is an independent document insert.


The potential bottleneck is the notification emit. 100 reviews saved means 100 socket emissions happening in rapid succession. Socket.IO can handle this, but if each emit triggers a DB write for the notification AND a socket broadcast, we're doing 200 DB operations in that burst. At scale, I'd debounce low-priority notifications or use a message queue (like BullMQ with Redis) — push notification jobs to a queue, process them asynchronously, decouple the review save latency from the notification latency.


There's also a connection pool limit with MongoDB — Mongoose defaults to 5 connections. Under 100 concurrent requests, you'd hit contention. I'd increase the pool size in Mongoose options: mongoose.connect(uri, { maxPoolSize: 50 }).

💬 Follow-Up

What if two admins update the same review at the same time — can that cause data corruption?

🎯 How to Respond

That's a classic lost update problem. MongoDB's findByIdAndUpdate is atomic at the document level, so no partial writes. But if Admin A reads the document, Admin B updates it, and then Admin A writes based on stale data, Admin B's update is silently overwritten. The fix is optimistic concurrency control — add a version field (or use Mongoose's built-in __v), include it in the query: Review.findOneAndUpdate({ _id, version: originalVersion }, updates). If the version doesn't match (someone else updated it), the update finds no document and returns null — you return a 409 Conflict to the client.

🔹 Error Handling & Security
Q10
Error Handling

How do you handle errors in Express? What's your global error handler look like, and how do you prevent stack traces from leaking to clients?

🔍 What the Interviewer Is Testing

Production readiness — separating operational errors (user did something wrong) from programmer errors (bug), and not leaking internal details.

✅ Strong Answer

All async controller functions are wrapped to forward errors to Express's error middleware via next(err) — or I use an asyncHandler wrapper that catches promise rejections automatically. At the end of the Express middleware chain, I have a global error handler with the (err, req, res, next) signature.


Inside it, I check process.env.NODE_ENV. In development, I send the stack trace for debugging. In production, I log the full error internally (to console or a logger) and only send a sanitized response: { success: false, message: err.message } — and only if err.isOperational is true (meaning I explicitly threw it). Unhandled programmer errors get a generic "Something went wrong" message. I also handle Mongoose-specific errors — CastError becomes a 400, ValidationError becomes a 400 with field-level messages, and duplicate key error (code 11000) becomes a 409.

💬 Follow-Up

What happens if a promise rejects inside an async route and you forget to use try/catch or asyncHandler?

🎯 How to Respond

In Express 4, an unhandled promise rejection inside a route handler won't crash the server but it also won't send a response — the request just hangs forever and the client times out. In Express 5 (now stable), uncaught async errors are automatically forwarded to the error middleware. But in Express 4, to handle this globally, you'd attach a process.on('unhandledRejection', (reason) => { ... }) listener that logs and optionally terminates the process gracefully. That's why the asyncHandler wrapper — it's a safety net that ensures any rejection hits next(err).

Q11
Security

Name three security vulnerabilities your app could have, and tell me what you did — or would do — to prevent each one.

🔍 What the Interviewer Is Testing

Security mindset beyond "we use JWT." They want real vulnerability awareness — NoSQL injection, XSS, CORS misconfiguration, rate limiting.

✅ Strong Answer

1. NoSQL Injection: MongoDB queries can be manipulated if user input is passed directly as objects. For example, a login query User.findOne({ email: req.body.email }) is vulnerable if an attacker sends { "email": { "$gt": "" } }. My fix: use express-mongo-sanitize middleware which strips out keys starting with $ or containing . from req.body, req.query, and req.params.


2. Overly permissive CORS: In early development I had cors({ origin: '*' }). In production, I locked it to the specific frontend origin. I also make sure sensitive routes require credentials, not just any origin.


3. No rate limiting on auth routes: Without rate limiting, a bot can attempt unlimited password guesses. I added express-rate-limit with a window of 15 minutes and a max of 10 attempts on /api/auth/login. If exceeded, it returns 429.


Additional: I use helmet middleware to set security headers — X-Content-Type-Options, X-Frame-Options, Strict-Transport-Security — all set automatically.

💬 Follow-Up

What's the difference between authentication and authorization, and which one is harder to get right?

🎯 How to Respond

Authentication is "who are you?" — verifying identity. Authorization is "what are you allowed to do?" — verifying permissions. Authorization is harder because it's context-dependent. Authentication is mostly solved by libraries like JWT or OAuth. Authorization requires you to model your business rules correctly — role hierarchies, ownership checks, time-based access, and the intersections. The subtle bugs live in authorization: checking the role but not the ownership, or checking the ownership but not whether the resource is in an allowed state. Those bugs in production mean data exposure, not just access denial.

🔹 Deployment
Q12
DockerAWS EC2

Walk me through your Docker setup. What's in your Dockerfile and docker-compose? Why do you use multi-stage builds?

🔍 What the Interviewer Is Testing

Whether you actually Dockerized this or just have a Dockerfile that someone else wrote. They want port mapping, volume understanding, multi-stage builds, and env var handling.

✅ Strong Answer

For the backend, my Dockerfile uses a two-stage build. Stage 1 uses node:18-alpine, copies package*.json, runs npm ci --only=production, then copies source. Stage 2 copies only the node_modules and source from stage 1 — this keeps dev dependencies out of the final image, cutting image size from ~400MB to ~120MB.


My docker-compose.yml has three services: backend (port 5000), frontend (served by nginx internally), and in development mongo (though in production I use MongoDB Atlas). The backend service takes environment variables from a .env file — env_file: .env — so secrets aren't baked into the image. I use named volumes for MongoDB data persistence in dev so the database survives container restarts.

In CI/CD (GitHub Actions), I build the Docker image, push to DockerHub, SSH into EC2, pull the new image, and run docker-compose up -d --no-deps backend to replace only the backend container without downtime on other services.
💬 Follow-Up

If you update environment variables on EC2, does the running container automatically pick them up?

🎯 How to Respond

No — environment variables are baked in at container start time. To pick up new env vars, you need to stop and re-create the container: docker-compose up -d --force-recreate backend. Just restarting the container isn't enough if you only changed the .env file on the host — docker-compose re-reads the env file only when it creates a new container. That's a common gotcha — I learned this when I rotated the MongoDB password and the app was still using the old one until I did a full container recreation.

Q13
Nginx

How is Nginx configured in your deployment? What does it actually do in your stack?

🔍 What the Interviewer Is Testing

Whether you understand Nginx as a reverse proxy, SSL termination point, and static file server — not just a "required thing for deployment."

✅ Strong Answer

Nginx sits in front of everything on port 443 (SSL). It does three jobs: SSL termination — handles TLS, so Express never sees HTTPS; routing — requests to /api/* are proxied to the Express container at localhost:5000, all other requests serve the React static build; and security headers — I set X-Frame-Options, Content-Security-Policy, and Strict-Transport-Security at the Nginx level.


The SSL certificate was provisioned via Certbot (Let's Encrypt) on the EC2 instance. Certbot auto-configured the Nginx server block for HTTPS and set up a cron job to auto-renew the cert every 90 days.


For Socket.IO, Nginx needed special config — WebSocket upgrade headers: proxy_http_version 1.1, proxy_set_header Upgrade $http_upgrade, proxy_set_header Connection "upgrade" — otherwise Socket.IO falls back to polling which is less efficient.

💬 Follow-Up

How do you handle zero-downtime deployments with Nginx and Docker?

🎯 How to Respond

In my current setup, there's a brief moment where the old container is stopped and the new one starts — maybe 2–5 seconds of downtime. True zero-downtime would require either: running two instances and Nginx load balancing between them (blue-green deployment), or using Docker Swarm / Kubernetes rolling updates. With blue-green, I'd start the new container on a different port, health-check it, update the Nginx upstream to point to the new port, reload Nginx with nginx -s reload (which is graceful — doesn't drop active connections), and only then stop the old container.

🔹 Performance & Scalability
Q14
Performance

A faculty member complains that the review dashboard takes 4 seconds to load. How do you debug and fix this?

🔍 What the Interviewer Is Testing

Systematic debugging approach — frontend bundle, network waterfall, API response time, database query time, N+1 queries.

✅ Strong Answer

I'd start with Chrome DevTools Network tab — is the 4 seconds in the initial HTML load, the JS bundle, the API call, or React rendering? If it's the API, I'd check the response time in the Network tab and compare with hitting the endpoint directly in Postman to isolate frontend overhead.


On the backend, I'd add timing logs around the DB query using console.time / timeEnd temporarily to see if MongoDB is slow. Most likely culprit: N+1 query. If I'm doing Review.find({ assignedFaculty: id }) and then a separate DB call inside a loop for each review's submitter info — that's 1 + N queries. Fix is .populate('submittedBy', 'name email') which Mongoose translates to a single $in query.


Frontend side: I'd check if the page is fetching data that it doesn't render immediately. If yes, lazy load with React.lazy and split the heavy component into a separate bundle chunk. Also check if we're re-fetching on every render — means a missing dependency array in useEffect or a new object reference being passed as a prop on each parent render.

💬 Follow-Up

How would you cache the review list so it doesn't hit MongoDB on every page load?

🎯 How to Respond

Short-term: RTK Query on the frontend has built-in caching — if the same query was made within keepUnusedDataFor seconds (default 60s), it serves from cache without a network request. Server-side: I'd add Redis in front of the MongoDB query. Key is something like reviews:faculty:${facultyId}:status:pending. First request hits MongoDB, stores result in Redis with a TTL of 30 seconds. Subsequent requests serve from Redis. Cache invalidation: when a review's status changes, I delete the relevant Redis key. The risk is stale data — a review gets updated but the cache hasn't expired. TTL-based expiry handles this automatically; explicit invalidation on writes is more precise but more complex.

Q15
Scalability

EduNexus currently has 50 users. If it goes to 50,000 users — what breaks first, and how would you redesign it?

🔍 What the Interviewer Is Testing

System design thinking — identifying single points of failure, stateful vs stateless architecture, horizontal scaling, and the Socket.IO stickiness problem.

✅ Strong Answer

First thing that breaks: Socket.IO. My current setup stores socket connections in memory on a single Node.js process. If I spin up two EC2 instances behind a load balancer, a user connected to Server A won't receive events emitted on Server B. The fix is Socket.IO's Redis adapter — all servers share a pub/sub channel via Redis, so an emit on Server A is received by clients connected to Server B.


Second bottleneck: single EC2 instance. Node.js is single-threaded. I can use cluster module to spawn multiple processes (one per CPU core) on the same instance, or better — run the EC2 behind an Application Load Balancer with sticky sessions enabled (for WebSocket) and multiple instances horizontally.


Third: MongoDB Atlas free tier. At 50K users with active reviews, I'd upgrade to a dedicated cluster with read replicas — route read queries to replicas, keep writes on the primary. Also add sharding on the reviews collection by submittedBy as the shard key.


Fourth: no CDN. Static React assets are served by Nginx on EC2. At scale, these go on S3 + CloudFront — edge-cached globally, zero load on EC2 for static files.

💬 Follow-Up

How does the Redis adapter for Socket.IO actually work under the hood?

🎯 How to Respond

When Server A calls io.to(userId).emit('notification', data), instead of only checking its local in-memory room map, with the Redis adapter it publishes the event to a Redis pub/sub channel. Every Socket.IO server is subscribed to that channel. Server B receives the published message and checks if any of its locally connected sockets are in the userId room — if yes, it delivers the event. So the actual WebSocket delivery still happens from the server that holds the connection; Redis is just the message bus coordinating which server needs to deliver to whom.

Q16
Caching & Rate Limiting

How would you add Redis caching to this project without breaking the existing data consistency guarantees?

🔍 What the Interviewer Is Testing

Cache invalidation strategy, read-through vs write-through patterns, and whether you understand that caching introduces eventual consistency.

✅ Strong Answer

I'd use the cache-aside (lazy loading) pattern. On a read request, check Redis first. Cache hit → return immediately. Cache miss → query MongoDB, store result in Redis with a TTL, return result. On any write (status update, new review), I explicitly delete (or update) the relevant cache key — don't wait for TTL to expire, because admin dashboards need fresh data immediately after an action.


The tricky part is key design. For GET /api/reviews?faculty=abc&status=pending&page=2, the cache key must encode all query parameters: reviews:faculty:abc:status:pending:page:2. On a bulk status update, I'd use Redis key pattern deletion: DEL reviews:faculty:abc:* to flush all paginated cache for that faculty.


I would NOT cache user-specific sensitive data like individual review content in a shared cache layer without namespacing by userId — that risks serving one user's private data to another if keys collide.

💬 Follow-Up

What's a cache stampede and how do you prevent it?

🎯 How to Respond

Cache stampede happens when a cached key expires and hundreds of requests simultaneously find a cache miss — they all hit MongoDB at once, overloading it. Three prevention strategies: (1) Mutex lock — only one request rebuilds the cache, others wait or get stale data. (2) Background refresh — a cron job refreshes the cache before TTL expires, so it never truly expires while data is actively used. (3) Stale-while-revalidate — serve the stale cached value immediately and asynchronously refresh in the background. This is what CDNs like CloudFront use natively.

🔹 Logging & Monitoring
Q17
Logging & Monitoring

How would you know if your production app is broken right now? What's your monitoring and alerting setup?

🔍 What the Interviewer Is Testing

Production maturity — structured logging, observability, not relying on users to report bugs. A common weak spot for junior developers.

✅ Strong Answer

Honestly, in the current state, my monitoring is basic — I'd know something is broken when I manually check EC2 or a user reports it. That's not production-grade, and here's what I'd add.


Structured logging with Winston or Pino — log every request with method, path, status, response time, and userId if authenticated. Output as JSON so logs are parseable by log aggregators. Use log levels: info for normal requests, warn for 4xx, error for 5xx.


Health check endpoint: GET /api/health that checks DB connectivity and returns status 200 with latency. An external uptime monitor (UptimeRobot, free tier) pings this every minute and sends an email alert if it goes down.


Error tracking: Integrate Sentry — it automatically captures unhandled exceptions, groups them by type, and shows a stack trace with request context. One line: Sentry.init({ dsn: '...' }) in the Express server.


Metrics: At scale, use PM2 for process monitoring (CPU, memory, restarts) and export metrics to Grafana or CloudWatch. Set CloudWatch alarms on EC2 CPU > 80% sustained for 5 minutes.

💬 Follow-Up

A bug only happens for one specific user in production. How do you debug it without exposing other users' data?

🎯 How to Respond

Structured logs with userId attached make this straightforward — I can filter logs by that userId without reading anyone else's data: grep '"userId":"abc123"' app.log. If using Sentry, I can search errors by userId from the Sentry dashboard. If I need to reproduce locally, I create a test user with similar role/data in a staging environment — never touch production data directly. If the bug is DB-state-dependent, I'd use MongoDB's aggregate pipeline to analyze that user's data in a read-only way, never running write operations on production to debug.

🔹 Debugging & Tricky Scenarios
Q18
DebuggingProduction

Tell me about the hardest bug you fixed in this project. Walk me through how you found it and fixed it.

🔍 What the Interviewer Is Testing

Debugging methodology, patience under ambiguity, and whether you have real war stories. Generic answers fail this question.

✅ Strong Answer (based on known project history)

The hardest one was the HTTP/2 protocol error on production login. The app worked perfectly locally. After deploying to EC2 with Nginx + Docker, the login API call returned ERR_HTTP2_PROTOCOL_ERROR in the browser. No 4xx, no 5xx — just a protocol error. The token was never received, so users couldn't log in at all.


My debugging process: First, I tested the API directly with Postman — it worked. So the problem was in the browser-to-Nginx-to-Express chain specifically. Next, I checked Nginx error logs on EC2 — saw upstream prematurely closed connection and stream reset errors. That pointed to a protocol mismatch. I read the Nginx docs — found that listen 443 ssl http2 tells Nginx to use HTTP/2 for both incoming and the upstream proxy connection. But Express is HTTP/1.1. Nginx was trying to speak HTTP/2 to Express, Express didn't understand it, and dropped the connection mid-response. Fix was one word: removed http2 from the Nginx listen directive. Deployed — login worked instantly.


Lesson: production bugs often live in the infrastructure layer, not your application code. Always trace the full request path, not just your code.

💬 Follow-Up

How would you have caught this before it hit production?

🎯 How to Respond

With a proper staging environment that mirrors production exactly — same Nginx config, same Docker networking, same SSL setup. The key gap was that I was testing locally without Nginx and without Docker networking. If I'd had a staging EC2 that was identical to production, I'd have caught it there. A smoke test in the CI/CD pipeline that calls the health check and the login endpoint via HTTPS after deployment would also catch it — the deployment would fail before going live. Automated E2E tests with Playwright that run against the staged environment would be the gold standard.
